# Azure SDK agent-friendliness benchmark snapshot

> Published: 2026-09-01
>
> Updated: 2026-09-02 with the complete multi-service Vally run

## Summary

- The refreshed multi-service run completed 230 trials across all 14 planned
  language and configuration shards.
- Azure MCP with general skills improved aggregate Prompt and Language Check
  rates over baseline. Adding SDK skills produced the highest Language Check
  rate, but Prompt Check changes remained mixed by language.
- Baseline and Azure MCP Program Checks passed completely. The full-skills
  Python Program Check was contaminated by injected skill templates and is not
  valid evidence about generated application buildability.
- More representative customer scenarios and broader service, language,
  harness, and model coverage are needed.

## Purpose

This report records one data point on whether an AI coding agent can produce
correct, idiomatic, and buildable Azure SDK projects. It does not determine
overall SDK agent-friendliness.

Baseline results are the primary signal. MCP and skills are secondary
configurations used to observe whether external guidance changes the outcome.

## Benchmark scenarios

The multi-service scenarios cover authentication, client setup, CRUD,
pagination, error handling, retries, polling, batch operations, messaging, and
event processing across data-plane and management-plane SDKs.

The Foundry scenarios cover agent lifecycle, file search, function tools,
project resource discovery, dataset lifecycle, evaluation runs, text
translation and transliteration, and single-document and batch document
translation.

Each scenario requests a complete project, testing an end-to-end developer task
rather than isolated API calls.

## Configurations

| # | Configuration | Coding-agent assistance |
|---:|---|---|
| 1 | Baseline | No Azure-specific tools or skills |
| 2 | Azure MCP + general skills | Azure MCP and general Azure skills |
| 3 | Azure MCP + general + SDK skills | Azure MCP, general Azure skills, and language-specific SDK skills |

For Foundry scenarios, configurations 2 and 3 also include Foundry MCP.

## Methodology

### Evaluation checks

The benchmark harness evaluates the generated project for each scenario using
the following check categories.

#### Prompt Checks

Prompt Checks cover scenario-specific requirements from the
`## Evaluation Criteria` section, including packages, clients, authentication,
operations, and error handling.

Examples for .NET scenarios include:

- Reference the required Azure SDK packages.
- Construct the requested client.
- Call the APIs needed to create, list, update, and delete a resource.

#### Language Checks

Language Checks cover SDK practices from `criteria/language/<language>.yaml`,
including authentication, asynchronous usage, error handling, and resource
management.

Examples for .NET scenarios include:

- Use `Azure.Identity` for token-based authentication.
- Use `await` instead of blocking with `.Result`.
- Use SDK-specific exceptions such as `RequestFailedException`.

#### Program Checks

Program Checks use language-specific commands for structural and build
validation.

For example, the .NET check runs:

- `dotnet build --nologo`

## Grading criteria and scoring

| Check type | What it evaluates | How grading works |
|---|---|---|
| Prompt Check | Scenario-specific packages, clients, APIs, authentication, and operations | An AI reviewer is instructed to mark the check passed only when it judges the requirement fully met. |
| Language Check | Language-specific authentication, asynchronous usage, error handling, and resource management | An AI reviewer is instructed to mark the check passed only when it judges the practice correctly applied. |
| Program Check | Compilation, build, lint, or validation commands | Exit code 0 passes; a nonzero exit, timeout, or execution failure fails. |

Prompt and Language Check results remain model judgments. The reviewer may
interpret partial or equivalent implementations differently across runs.

Each applicable check contributes one equally weighted pass or fail point. The
pass rate is:

`passed checks / applicable checks`

Prompt, Language, and Program Checks remain separate. Skipped checks are
excluded, and infrastructure failures are reported separately. Cross-language
totals are informational because scenario and criteria inventories differ.

### Interpreting the results

Program Checks provide the strongest evidence of buildability. Prompt Checks
measure task completion, while Language Checks provide a supporting signal for
SDK practices. The categories remain separate; the report does not calculate a
combined weighted score.

Treat differences of a few percentage points as directional, not conclusive.
The results suggest assisted configurations may improve some outcomes, but
single runs and the combined MCP-and-skills setup cannot establish a general or
skill-specific improvement.

## Assumptions and limitations

- This benchmark is one data point. Each scenario runs once per configuration,
  and LLM-reviewed checks are nondeterministic.
- Many scenarios specify the expected package, client, or SDK pattern. Results
  are stronger evidence of implementation than independent API discovery.
- Method-specific criteria can reject functionally equivalent SDK patterns and
  may lag current SDK APIs. Some failed checks can therefore reflect rubric
  specificity or staleness rather than failure to complete the requested task.
- Scenario inventories differ by language and cover common tasks rather than
  every library or usage pattern.
- The local-code focus limits opportunities for MCP to help and does not measure
  general tool effectiveness.

## Next steps

Building a more realistic assessment of Azure SDK agent-friendliness requires
significant investment. Priorities include:

- Expand representative customer scenarios across five or more programming
  languages and more than 200 Azure services.
- Run the same scenarios with different agent harnesses to identify
  harness-specific effects.
- Run the same scenarios with different LLM models to measure model
  sensitivity.

## Multi-service Azure SDK results

The refreshed results come from
[Vally run 33565990412](https://github.com/weidongxu-microsoft/azure-skill-evals/actions/runs/33565990412).
It used Vally 0.14, `gpt-5.6-sol`, one trial per scenario and configuration, 79
scenarios, and the same migrated Hyoka prompts and criteria. Go has no SDK-skills
configuration, producing 230 trials rather than 237. Fan-in collected every
expected result without integrity errors.

### Results

#### Prompt Checks

| Language | Sets | Baseline | Azure MCP + general skills | Azure MCP + general + SDK skills |
|---|---:|---:|---:|---:|
| Python | 19 | 161/172 (93.6%) | 164/172 (95.3%) | 167/172 (97.1%) |
| JavaScript/TypeScript | 14 | 112/126 (88.9%) | 122/126 (96.8%) | 122/126 (96.8%) |
| Java | 19 | 154/167 (92.2%) | 163/167 (97.6%) | 164/167 (98.2%) |
| .NET | 20 | 107/135 (79.3%) | 109/135 (80.7%) | 105/135 (77.8%) |
| Go | 7 | 44/46 (95.7%) | 45/46 (97.8%) | N/A |
| **Total** | **79** | **578/646 (89.5%)** | **603/646 (93.3%)** | **558/600 (93.0%)** |

The SDK-skills configuration was not run for Go because no Azure SDK for Go
plugin was available.

#### Program Checks

| Language | Baseline | Azure MCP + general skills | Azure MCP + general + SDK skills |
|---|---:|---:|---:|
| Python | 19/19 (100%) | 19/19 (100%) | 0/19 (0%)<sup>*</sup> |

<sup>*</sup> The full-skills Python command ran `python -m compileall -q .`, which also
compiled injected skill assets. Two template files contained literal
placeholders such as `{{resource_name}}`, causing all 19 checks to fail for the
same harness reason. Excluding those contaminated checks, the full-skills
configuration passed 66/67 (98.5%) Program Checks; the remaining failure was
one .NET project build.

#### Duration

Durations use the 72 non-Go scenarios shared by all three configurations.

| Configuration | Average per evaluation | Difference from baseline |
|---|---:|---:|
| Baseline | 1.29 min | - |
| Azure MCP + general skills | 1.47 min | +0.18 min (+14%) |
| Azure MCP + general + SDK skills | 1.52 min | +0.23 min (+18%) |

### Key findings

- Across all 79 baseline and Azure MCP sets, Prompt Checks increased from 89.5%
  to 93.3%, while Language Checks increased from 81.5% to 87.6%.
- Across the 72 three-way sets, Prompt Checks were 89.0% for baseline and 93.0%
  for both assisted configurations. The full configuration had the highest
  Language Check rate at 89.9%, 8.4 points above baseline.
- Results varied by language. SDK skills produced the highest Prompt and
  Language Check rates for Python and Java, tied the general configuration for
  TypeScript Prompt Checks, and reduced .NET Prompt Checks below baseline.
- Baseline and Azure MCP passed every Program Check. After excluding the
  contaminated Python checks, the full configuration passed 98.5%.
- On the 72 comparable non-Go sets, assisted configurations took 14% to 18%
  longer per evaluation than baseline.
