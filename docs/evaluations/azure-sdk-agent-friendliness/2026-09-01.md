# Azure SDK agent-friendliness benchmark snapshot

> Published: 2026-09-01

## Purpose

This report records one data point on whether an AI coding agent can produce
correct, idiomatic, and buildable Azure SDK projects. It does not determine
overall SDK agent-friendliness.

Baseline results are the primary signal. MCP and skills are secondary
configurations used to observe whether external guidance changes the outcome.

## Configurations

| # | Configuration | Coding-agent assistance |
|---:|---|---|
| 1 | Baseline | No Azure-specific tools or skills |
| 2 | Azure MCP + general skills | Azure MCP and general Azure skills |
| 3 | Azure MCP + general + SDK skills | Azure MCP, general Azure skills, and language-specific SDK skills |

For the Azure AI Foundry SDK tests in Data point 2, configurations 2 and 3 also
include Foundry MCP.

## Methodology

### Prompt set

The prompts cover authentication, client construction, CRUD, pagination, error
handling, retries, polling, batch operations, and event processing. They test
complete developer tasks rather than isolated API calls.

### Checks

#### Prompt Checks

Each item in a prompt's `## Evaluation Criteria` is an independent requirement.
An LLM reviewer checks the generated project for the requested packages,
clients, authentication, operations, and error handling. These checks measure
task completion and API usability.

#### Language Checks

The checks in `criteria/language/<language>.yaml` apply to the matching language.
An LLM reviewer evaluates language-specific authentication, asynchronous usage,
exception handling, and resource management. These checks measure idiomatic SDK
integration.

#### Program Checks

The configured build command restores and compiles the generated project. These
checks measure whether package choices, API signatures, dependencies, and
project structure work together.

## Grading criteria and scoring

Each applicable criterion produces an equally weighted pass or fail point. The
pass rate is:

```text
passed checks / applicable checks
```

Prompt, Language, and Program Checks remain separate. Skipped checks are
excluded, and infrastructure failures are reported separately. Cross-language
totals are informational because prompt and criteria inventories differ.

## Assumptions and limitations

- A benchmark is one data point and cannot establish overall SDK
  agent-friendliness.
- Each prompt runs once per configuration; model variability is not measured.
- LLM-reviewed checks are nondeterministic and use one reviewer model.
- Many prompts specify the expected package, client, or SDK pattern. Results are
  stronger evidence of implementation than independent API discovery.
- Prompt inventories differ by language, so cross-language totals are
  informational.
- The prompts cover common tasks, not every library or usage pattern.
- The local-code focus limits opportunities for MCP to help and does not measure
  general tool effectiveness.

## Data point 1: Multi-service Azure SDKs

**Completed:** 2026-08-28  
**Source:** [ronniegeraghty/hyoka#656](https://github.com/ronniegeraghty/hyoka/pull/656)

### Scope

The primary run produced 216 evaluations across 72 comparison sets. Seven
controlled retries completed, four were selected, and the final dataset contains
207 evaluations across 69 complete sets.

The environment used Copilot SDK v1, Copilot CLI v1.0.81-11, and Azure MCP
3.0.0-beta.38. Program Checks and Go were unavailable, and .NET Language Checks
were not configured. Three unresolved sets were excluded: .NET managed identity,
Java storage account management, and JavaScript/TypeScript Event Hubs.

### Results

#### Prompt Checks

| Language | Sets | Baseline | Azure MCP + general skills | Azure MCP + general + SDK skills |
|---|---:|---:|---:|---:|
| Python | 19 | 150/172 (87.2%) | 156/172 (90.7%) | 159/172 (92.4%) |
| JavaScript/TypeScript | 13 | 103/118 (87.3%) | 102/118 (86.4%) | 104/118 (88.1%) |
| Java | 18 | 140/159 (88.1%) | 146/159 (91.8%) | 149/159 (93.7%) |
| .NET | 19 | 109/129 (84.5%) | 101/129 (78.3%) | 109/129 (84.5%) |
| **Total** | **69** | **502/578 (86.9%)** | **505/578 (87.4%)** | **521/578 (90.1%)** |

#### Language Checks

| Language | Baseline | Azure MCP + general skills | Azure MCP + general + SDK skills |
|---|---:|---:|---:|
| Python | 77/95 (81.1%) | 84/95 (88.4%) | 90/95 (94.7%) |
| JavaScript/TypeScript | 88/130 (67.7%) | 92/130 (70.8%) | 91/130 (70.0%) |
| Java | 163/216 (75.5%) | 179/216 (82.9%) | 177/216 (81.9%) |
| .NET | Not configured | Not configured | Not configured |

#### Duration

| Configuration | Average per evaluation | Difference from baseline |
|---|---:|---:|
| Baseline | 4.01 min | - |
| Azure MCP + general skills | 5.12 min | +1.11 min (+28%) |
| Azure MCP + general + SDK skills | 4.69 min | +0.67 min (+17%) |

### Key findings

- Baseline passed 86.9% of Prompt Checks. In this guided prompt set, the agent
  usually completed the requested SDK tasks without Azure-specific assistance.
- Across the 69 complete sets, the Prompt Check pass rate was 86.9% for
  baseline, 87.4% with Azure MCP and general skills, and 90.1% after adding
  language-specific SDK skills. The assisted configurations were 0.5 and 3.2
  percentage points above baseline.
- Differences varied by language. Adding SDK skills scored higher for Python
  and Java, nearly matched baseline for JavaScript/TypeScript, and tied it for
  .NET.
- Assisted configurations took longer than baseline.
- All 697 primary and 29 retry Azure MCP calls succeeded without a timeout.

## Data point 2: Azure AI Foundry SDK

**Completed:** 2026-09-01

**Source:** [weidongxu-microsoft/hyoka#4](https://github.com/weidongxu-microsoft/hyoka/pull/4)

### Scope

The primary baseline run produced 40 evaluations: 10 each for .NET, Java,
JavaScript/TypeScript, and Python. This data point measures only the baseline
configuration. It does not estimate the effect of Foundry MCP, general Azure
skills, or language-specific SDK skills.

The run used Foundry comparison commit `456b26ea`, generator and reviewer model
`gpt-5.6-sol`, Copilot SDK v1, and checksum-verified Copilot CLI v1.0.81-11.
The build environment used .NET SDK 8.0.424, Java 21 with Maven 3.8.3, Node.js
24.18.0 with npm 10.8.0, and Python 3.12.10.

Baseline sessions had no configured Azure-specific skills or MCP servers.
General Copilot-provided web search and GitHub tools remained available.

### Results

#### Prompt Checks

|---|---:|---:|
| .NET | 10 | 89/90 (98.9%) |
| Java | 10 | 90/90 (100%) |
| JavaScript/TypeScript | 10 | 81/88 (92.0%) |
| Python | 10 | 78/80 (97.5%) |
| **Total** | **40** | **338/348 (97.1%)** |

#### Language Checks

### Run health

- All 40 primary evaluation reports were preserved.
- .NET and Java completed without generation, review, session, or build
  infrastructure failures.
- Python `evaluation-run` generated 60 files. All six review requests exceeded
  the reviewer token limit, so its Prompt and Language Checks are unavailable
  and excluded from the applicable-check denominators.
- JavaScript/TypeScript `file-search` and `evaluation-run` reached 51/50 session
  actions and returned partial results. User-approved reruns with a 100-action
  limit are in progress; the primary results above remain unchanged until the
  reruns are reconciled.
- JavaScript/TypeScript transliteration issued one malformed PowerShell command
  and corrected it on the next action.
- No configured MCP server failed to load or timed out. Cleanup reported missing
  session files and terminated orphaned Copilot processes after the language
  runs, but all expected primary reports were retained.

### Key findings

- Baseline passed 97.1% of available Prompt Checks. In this guided Foundry
  prompt set, the coding agent usually implemented the requested task without
  Azure-specific assistance.
- Language Checks passed at a lower rate, 71.4%. Repeated failures came from
  broad language criteria such as explicit diagnostic logging, typed
  service-exception handling, dependency BOM usage, and prescribed LRO
  patterns.
- Some language rules conflict with service-specific patterns. Examples include
  requiring `begin*` methods where an SDK exposes `createAndPoll` or
  `startTranslation`, and requiring token credentials where a Translation
  scenario uses key authentication. These failures may reflect rubric breadth
  as well as generated-code quality.
- Program Checks passed 98.0%. The only build failure was the action-limited
  JavaScript/TypeScript `evaluation-run` case.
- The baseline-only scope cannot show whether Foundry MCP or skills improve the
  results.
